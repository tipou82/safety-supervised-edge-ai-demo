The Q&A watchdog replaces the GPIO heartbeat — no heartbeat GPIO is used.

### Power and Ground Pins

| Physical Pin | Function | Connection |
|-------------|----------|------------|
| Pin 1 or 17 | 3.3V Power | I2C pull-up resistors (4.7 kΩ to 3.3V on SDA and SCL) |
| Pin 2 | 5V Power | Ultrasonic sensor VCC |
| Pin 6 | Ground | Common ground (Pi400, sensors, LEDs, I2C) |
| Pin 9 | Ground | Additional ground reference |

### GPIO Configuration Details

**I2C Q&A Watchdog — Master (GPIO 2 SDA, GPIO 3 SCL)**
- **Mode**: I2C master
- **Speed**: 100 kHz (standard mode; 400 kHz fast mode acceptable)
- **Pull-ups**: External 4.7 kΩ to 3.3V on both SDA and SCL
- **Pi400 slave address**: 0x40
- **Register map**:
  - `0x00` (read): 4-byte seed generated by Pi400
  - `0x01` (write): 4-byte response computed by Pi5
- **Response algorithm**: `response = seed XOR 0xA5A5A5A5`
- **Timing**: Response shall arrive 50–100 ms after last correctly acknowledged response

**Emergency Stop Input (GPIO 25)**
- **Mode**: GPIO input
- **Pull**: Internal pull-up (50 kΩ)
- **Active State**: Active-low (0V = emergency stop asserted)
- **Polling Rate**: 100 Hz by actuator_node
- **Response Time**: <30 ms from assertion to motor disable
- **Failure Mode**: Fail-safe — wire disconnection pulls HIGH = inactive; Pi400 asserts LOW actively

**Green LED — NORMAL State (GPIO 17)**
- **Mode**: GPIO output, initially LOW
- **Active State**: HIGH = LED ON
- **Driven by**: health_node on Pi5

**Yellow LED — DEGRADED State (GPIO 27)**
- **Mode**: GPIO output, initially LOW
- **Active State**: HIGH = LED ON
- **Driven by**: health_node on Pi5

**Red LED — SAFE STATE (GPIO 22, wired-OR)**
- **Mode**: GPIO output
- **Active State**: HIGH = LED ON
- **Driven by**: actuator_node on Pi5 OR safe_state_ctrl on Pi400 (wired-OR via diodes)
- **Wiring**: GPIO 22 → 150 Ω → 1N4148 → LED anode (see wiring.md for diode-OR detail)

**Grove Ultrasonic Ranger SIG (GPIO 23)**
- **Protocol**: Single-wire — GPIO 23 acts as output for trigger, then input for echo
- **Trigger**: 10 µs HIGH pulse on GPIO 23 (output mode)
- **Echo**: Measure HIGH duration on GPIO 23 (input mode) after trigger
- **Voltage**: 3.3 V (sensor powered from 3.3 V pin) — no voltage divider required
- **Range**: 2–350 cm

## Raspberry Pi 400 (QNX Supervisor Domain)

### GPIO Allocation Table

| GPIO # | Physical Pin | Function | Direction | Signal Type | Component | Safety Critical |
|--------|-------------|----------|-----------|-------------|-----------|-----------------|
| GPIO 2  | Pin 3  | I2C SDA — Q&A watchdog (slave) | Bidirectional | I2C | qnx_wdg_server | **YES** |
| GPIO 3  | Pin 5  | I2C SCL — Q&A watchdog (slave) | Input | I2C clock | qnx_wdg_server | **YES** |
| GPIO 22 | Pin 15 | Red LED — SAFE STATE (wired-OR with Pi5 GPIO 22 via diode) | Output | Digital | safe_state_ctrl | No |
| GPIO 25 | Pin 22 | Emergency stop output (active-low) | Output | Digital | safe_state_ctrl | **YES** |

### GPIO Configuration Details

**I2C Q&A Watchdog — Slave (GPIO 2 SDA, GPIO 3 SCL)**
- **Mode**: I2C slave at address `0x40`
- **Register map**:
  - `0x00` (read by Pi5): current 32-bit seed (refreshed each cycle)
  - `0x01` (write by Pi5): received response for validation
- **Seed generation**: New random 32-bit value generated at start of each watchdog cycle
- **Validation**: `expected = seed XOR 0xA5A5A5A5`; Pi400 checks received value and timing
- **Pull-ups**: Provided by Pi5 side (4.7 kΩ to 3.3V); Pi400 does not need additional pull-ups

**Emergency Stop Output (GPIO 25)**
- **Mode**: GPIO output
- **Default State**: LOW (asserted) at boot — fail-safe
- **Active State**: Active-low (0V = emergency stop active)
- **Drive Strength**: 2 mA
- **Released**: Only after Q&A watchdog initialises and system transitions to NORMAL

**Red LED — SAFE STATE (GPIO 22, wired-OR)**
- **Mode**: GPIO output
- **Active State**: HIGH = LED ON
- **Driven by**: safe_state_ctrl on Pi400 OR actuator_node on Pi5 (wired-OR via diodes)
- **Asserted when**: failure_counter reaches 3 → SAFE_STATE

### Q&A Watchdog Timing Parameters (Pi400 authoritative)

| Parameter | Value | Notes |
|---|---|---|
| Window period | 100 ms | Time from last correct response to timeout |
| Open window start | 50 ms | Responses before this are too early |
| Valid window | 50–100 ms | Response must arrive in this range |
| Failure counter increment | +1 | Too early, too late, or wrong answer |
| Failure counter decrement | −1 | After 2 consecutive correct responses |
| SAFE_STATE threshold | 3 | failure_counter ≥ 3 → assert e-stop + red LED |

## GPIO Design Rationale

### Why I2C Q&A Watchdog Instead of GPIO Heartbeat

| Aspect | GPIO Heartbeat | I2C Q&A Watchdog |
|---|---|---|
| Protocol complexity | Simple toggle | Seed/response challenge |
| Fault coverage | Detects stuck-at, missing | Also detects wrong-answer (SW corruption) |
| ASIL relevance | Common pattern | Stronger diagnostic coverage |
| Window enforcement | Timeout only | Open window + closed window |
| HW required | 1 wire | 2 wires (SDA + SCL) + pull-ups |

The Q&A watchdog provides stronger diagnostic coverage: a Linux process can reproduce the correct response only if it is running correctly and has access to the seed. A stuck-at or frozen process cannot generate a valid in-window response.

### Why Active-Low for Emergency Stop

Fail-safe: wire disconnection = open circuit. Pi5 GPIO 25 has internal pull-up, so disconnection reads HIGH = inactive. Pi400 must actively drive LOW to assert e-stop. Loss of Pi400 (or wire fault) → e-stop is NOT asserted, which is a known SPOF documented in `docs/ffi_argument.md`.

### Why Wired-OR for Red LED

Both Pi5 (application domain) and Pi400 (safety domain) must be able to independently assert the SAFE STATE indicator without requiring cooperation from the other domain. Diode isolation prevents back-current when one driver is LOW while the other is HIGH.

## Failure Mode Analysis

| Signal | Fault | Detection | Mitigation |
|--------|-------|-----------|------------|
| I2C SDA/SCL | Wire break or short | I2C NACK / no response | Pi400 treats missing response as timeout → failure_counter++ |
| I2C Q&A response | Wrong answer | Pi400 validates response | failure_counter++ |
| I2C Q&A timing | Response too early or late | Pi400 checks window | failure_counter++ |
| E-Stop output (Pi400 GPIO 25) | GPIO driver stuck high | Pi5 cannot enter safe state | **SPOF — accepted for demo** |
| E-Stop input (Pi5 GPIO 25) | Wire disconnection | Pull-up → HIGH = inactive | Fail-safe by wire, but e-stop lost |
| Red LED diode circuit | Diode short | Both sources can see back-current | 150 Ω series resistor limits current |
| Ultrasonic ECHO | 5V damage to GPIO | No voltage divider (3.3V sensor) | No risk — sensor powered at 3.3V |

## GPIO Testing Procedure

### Continuity Test
1. Power off both Pis
2. Use multimeter to verify:
   - Pi5 GPIO 2 (Pin 3) connected to Pi400 GPIO 2 (Pin 3) — I2C SDA
   - Pi5 GPIO 3 (Pin 5) connected to Pi400 GPIO 3 (Pin 5) — I2C SCL
   - Pi5 GPIO 25 (Pin 22) connected to Pi400 GPIO 25 (Pin 22) — e-stop
   - 4.7 kΩ pull-up resistors present on SDA and SCL to 3.3V
   - Common ground between Pi5 Pin 6 and Pi400 Pin 6

### Voltage Test
1. Power on both Pis
2. Measure I2C SDA/SCL — should read ~3.3V when idle (pulled high)
3. Measure e-stop GPIO (Pi400 GPIO 25) — should read 0V (asserted at boot)
4. After supervisor initialises — should read 3.3V (released)

### Functional Test
1. Run Q&A watchdog smoke test (`pi400_supervisor/scripts/i2c_wdg_test.py`) — TBD M2
2. Confirm seed read and response write on I2C bus
3. Confirm failure counter increments on bad answer
4. Confirm SAFE_STATE asserted on failure_counter ≥ 3
