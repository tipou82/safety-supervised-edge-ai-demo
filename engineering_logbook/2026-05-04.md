## Design Decisions

### Safety Wording Strategy

**Implemented consistent terminology**:
- ✅ "ASIL-B-inspired monitoring path" (NOT "ASIL-B path")
- ✅ "FFI-inspired architectural measures" (NOT "certified FFI")
- ✅ "demonstrator" (NOT "safety-certified system")
- ✅ "QNX-inspired supervisor" (acknowledging Linux fallback)
- ✅ Explicit disclaimers in every safety document

**Rationale**: Honesty and technical accuracy are paramount. Overclaiming would be obvious to interviewers with safety-critical background. Better to demonstrate understanding of concepts and honest assessment of limitations.

### Architectural Decisions

**Dual-Processor Separation**
- **Decision**: Pi5 for Linux/ROS2 (development domain), Pi400 for QNX supervisor (safety monitoring)
- **Rationale**: Physical separation provides strongest FFI spatial independence for demonstrator budget
- **Trade-off**: Increased cost and wiring complexity vs. single-processor partitioning
- **Alternative Considered**: QEMU/KVM virtualization with I/O passthrough - rejected due to lack of determinism guarantees

**GPIO for Safety Signals**
- **Decision**: Use simple GPIO heartbeat instead of Ethernet or USB communication
- **Rationale**: Simpler protocol is easier to analyze and monitor deterministically
- **Limitation**: No redundancy, single point of failure - accepted for demonstrator

**CRC32 for Data Integrity**
- **Decision**: Use CRC32 (not CRC16 or cryptographic hash)
- **Rationale**: Good balance of diagnostic coverage (>99.999%) and computational cost
- **Limitation**: Does not detect malicious tampering - acceptable for non-adversarial demo

**State Machine with 4 States**
- **Decision**: NORMAL, WARNING, DEGRADED, SAFE_STATE
- **Rationale**: Graceful degradation demonstrates understanding of fault tolerance
- **Alternative Considered**: Binary safe/unsafe - rejected as too simplistic for portfolio piece

### Requirements Approach

**Traceability from Start**
- **Decision**: Create traceability.csv during initialization, not as afterthought
- **Rationale**: Demonstrates systems engineering discipline, ensures testability
- **Benefit**: Forces clarity on verification strategy for each requirement

**SysML v2 Model**
- **Decision**: Include SysML architecture model (even if not fully executable)
- **Rationale**: Shows familiarity with modern MBSE tools, common in aerospace/automotive
- **Limitation**: SysML v2 tooling immature - may need to regenerate in v1 format

**YAML for Interfaces**
- **Decision**: Use YAML (not Excel or Word) for interface specifications
- **Rationale**: Machine-readable, can be parsed by test scripts or code generators
- **Benefit**: Demonstrates tooling mindset

## Technical Challenges Identified

### Hardware Integration (Future)

**Pi400 GPIO Access**
- Pi400 is a keyboard-integrated board, GPIO header less accessible than Pi 4
- May need ribbon cable extender for prototyping
- Alternative: Use Pi 4 instead of Pi400 for easier GPIO access

**QNX BSP for Raspberry Pi**
- QNX 7.1 support for Raspberry Pi exists but is not official/certified
- May need to implement Linux fallback with PREEMPT_RT kernel instead
- Decision: Document QNX design, implement Linux fallback first, port to QNX if time permits

**Voltage Divider for Ultrasonic ECHO**
- HC-SR04 outputs 5V on ECHO pin, Pi GPIO is 3.3V
- Voltage divider (1kΩ + 2kΩ) required for each ECHO pin
- Could also use dedicated level shifter chip for cleaner solution

### Software Architecture (Future)

**ROS2 Humble on Raspberry Pi 5**
- Pi5 is well-supported by Ubuntu 22.04
- ROS2 Humble binary packages available
- GPU acceleration for AI inference (MobileNet) via TensorFlow Lite or ONNX Runtime

**Watchdog Implementation in QNX**
- Need to decide: POSIX timers, QNX-specific TimerTimeout, or hardware watchdog timer
- If using QNX, priority inheritance for watchdog thread critical
- If using Linux fallback, SCHED_FIFO with isolcpus for core isolation

**CRC32 Library**
- QNX: Use standard zlib CRC32 or implement simple table-based CRC
- Linux: zlib available, or Boost CRC for C++
- Consistency: Same CRC polynomial on both sides (IEEE 0xEDB88320)
