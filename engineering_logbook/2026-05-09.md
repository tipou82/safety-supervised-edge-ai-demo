## M3.1 — StateEvaluator C++20 Implementation

### Decision: Convert decision_node from Python to C++20

The M3 spec called for a deterministic C++20 StateEvaluator. The existing Python decision_node was a placeholder, so conversion had low risk.

**Package structure:**
```
src/decision_node/
  include/decision_node/state_evaluator.hpp  ← pure logic, no ROS2 deps
  src/state_evaluator.cpp
  src/decision_node.cpp                       ← ROS2 node wrapper
  test/test_state_evaluator.cpp               ← gtest unit tests
  CMakeLists.txt                              ← ament_cmake, C++20
  package.xml
```

**StateEvaluator design:**
- Pure C++ class — no ROS2, no GPIO, no side effects
- Priority-ordered rules evaluated top-down (SAFE_STATE latch → SAFE_STATE trigger → INIT → DEGRADED → WARNING → NORMAL)
- Thresholds: WARNING < 0.50 m, SAFE_STATE < 0.15 m (bench-test assumptions, not safety-validated)
- `watchdog_failure_counter` wired to 0 in M3 — Pi400 slave deferred to M5
- `camera_valid = false` in M3 — camera_ai_node is a placeholder → system runs in DEGRADED correctly
- GPIO 25 e-stop NOT modelled in StateEvaluator — independent hardware layer in actuator_node (FFI boundary upheld)

**Velocity scaling:**

| State | vel_scale |
|---|---|
| INIT | 0.0 |
| NORMAL | 1.0 |
| WARNING | 0.5 |
| DEGRADED | 0.2 |
| SAFE_STATE | 0.0 |

## M3.2 — State Transition Verification (Hardware)

### Issue: Green LED ON and Red LED OFF in SAFE_STATE

**Problem**: After launch, `decision_node` correctly reported SAFE_STATE, but:
- Green LED remained ON (health_node drove it in `__init__` without observing state)
- Red LED remained OFF (actuator_node only drove it on hardware GPIO 25 assertion, not on software SAFE_STATE)

**Root cause**: health_node and actuator_node had no subscription to `/system_state` — they were unaware of the software state machine output.

**Fix**:
- `health_node`: added subscription to `/system_state`; green LED OFF when state = SAFE_STATE
- `actuator_node`: added subscription to `/system_state`; red LED ON when state = SAFE_STATE OR GPIO 25 asserted (wired-OR logic in software mirroring hardware diode-OR)
- `_update_red_led()` helper ensures consistent LED state from both triggers

### Issue: `lgpio.error: 'GPIO busy'` on relaunch

**Problem**: After Ctrl+C on the launch, health_node and actuator_node crashed on next launch with `GPIO busy` — GPIO pins still claimed by lingering processes.

**Root cause**: ROS2 node cleanup (`destroy_node()`) was not called because the previous launch was killed abruptly, leaving lgpio handles open in the kernel.

**Fix**:
```bash
pkill -9 -f health_node; pkill -9 -f actuator_node; sleep 2
```
If persistent: `sudo reboot` clears all GPIO handles.

simplejpeg (picamera2 dependency) was a system package compiled against numpy 1.x.

## M5 — E-Stop Signal Path Verification

### Method

The e-stop path was verified during M5 acceptance test step 2:
- `health_node` was stopped (simulating watchdog client failure)
- Pi400 `qnx_wdg_server.py` detected 3 consecutive Q&A failures
- Pi400 asserted GPIO 25 LOW (active-low e-stop output)
- Pi5 `actuator_node` (polling GPIO 25 at 100 Hz) logged:
  `[WARN] E-STOP ASSERTED (GPIO 25 LOW) — safe state`
- Red LED ON confirmed physically

This constitutes full end-to-end verification of the e-stop signal path:
**Pi400 GPIO 25 (Pin 22) → wire → Pi5 GPIO 25 (Pin 22) → actuator_node**

### Additional one-liner check (GPIO 25 direct read on Pi5)

With Pi400 watchdog server asserting (after stopping health_node):
```bash
python3 -c "
import lgpio; h=lgpio.gpiochip_open(4)
lgpio.gpio_claim_input(h,25,lgpio.SET_PULL_UP)
print('GPIO 25 =', lgpio.gpio_read(h,25))
lgpio.gpiochip_close(h)"
```
Expected: `GPIO 25 = 0` (asserted LOW by Pi400)
After Pi400 releases: `GPIO 25 = 1`
